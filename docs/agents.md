# Agents and resources

How Mirador reopens agents after a restart, lets idle ones sleep, opens several at once without filling the memory, gives each terminal its own systemd scope and turns off MCP servers per project. The summary is in the [README](../README.md#what-it-does).

## Reopening agents after a restart

While Mirador runs, it keeps one record per open agent terminal (workspace, folder, size and its pi session file once known) in `~/.local/state/mirador/open-agents.json` (`$XDG_STATE_HOME/mirador/open-agents.json`), rewritten whole on every change with mode 0600, so it survives a crash, an out-of-memory kill or `kill -9`. Bash terminals are not recorded, and scrollback is not restored.

- Closing an agent (✕) removes its record at once. An agent that exits by itself (code below 128) loses its record 5 seconds later, so a server killed in the same moment still finds it. An agent ended by a signal (an out-of-memory kill takes the whole session, agents possibly first) or with a code of 128 or more keeps its record until you close its terminal. Stopping Mirador (`mirador stop`, SIGINT or SIGTERM) keeps the records.
- The attention bridge inside each agent tells Mirador its current pi session file when it connects, on every new session (`/new`, `/resume`, `/fork`) and at the end of every turn (pi creates the file at the first message). Mirador keeps it only when it is an absolute path to an existing `.jsonl` file.
- At startup Mirador reopens the recorded agents one after another, 2 seconds apart and through the launch gate (see [Opening many agents without filling the memory](#opening-many-agents-without-filling-the-memory)), each with `--session <file>` when its session file still exists (for a plain `gentle-shell` or `pi` `agentCommand`; others start a fresh session). When several records name the same session file, only the first continues it; the others start a fresh session and Mirador logs it. A record whose workspace or folder no longer exists is dropped and logged. The reopened terminals replace the old records. With systemd scopes (below), Mirador first stops the scopes those agents ran in during the previous run, since after a crash they can still be running; an agent whose scope still runs after that is not reopened (its record stays and Mirador logs it), so one session never runs twice.
- The file names the `config.json` that wrote it: a Mirador started with another config leaves it untouched, and records of a config that no longer exists are discarded.

To start without the previous agents, stop Mirador and delete the file.

### Sleeping agents (lazy restore)

Each record also keeps its agent's last attention state (`lastState`), written about a second after it changes, so a crash knows it too: `waiting` (a dialog or a guarded command waits for your answer), `finished` (its turn ended, seen or not), or `working` (the bridge reported and nothing waits: a turn under way, or a session that has not finished a turn yet). It is absent while unknown (no bridge, nothing reported yet) and in files written before this. Reports that arrive once Mirador is stopping are ignored, so pi's goodbye does not erase what the agent was doing.

At startup only agents that were working, waiting or unknown reopen (through the launch gate, as above). The ones that had **finished** their turn stay **dormidos / sleeping**: no process and no scope, their record and session file kept across further restarts until you wake or forget them. The previous run's scopes are still stopped first, sleepers included, and an agent still running is neither reopened nor listed as sleeping.

- In **Desarrollo / Development** each workspace group ends with **💤 Dormidos (N) / 💤 Sleeping (N)** (a workspace whose agents all sleep gets a group of its own). It opens a dialog with **Despertar / Wake** and **Olvidar / Forget** per agent and **Despertar todos / Wake all**. **Seguimiento / Tracking** lists them in its dock, under **Cerrados, dormidos y fuera de Mirador / Closed, sleeping and outside Mirador**, with the same actions.
- **Despertar** reopens the agent exactly as the restore would, continuing its saved session, through the launch gate: while other agents open it waits its turn instead of being refused, and the loading bar says **⏳ Despertando agentes / ⏳ Waking agents**. **Despertar todos** wakes them in batches. What the gate does not open (low memory, Pausar) sleeps on. A woken agent counts as working until it finishes a turn, so it reopens at the next start until then.
- **Olvidar** asks first, then drops the record; the pi session file stays where pi keeps it.
- Opening an agent another way (by hand, a batch, a delegation) in a sleeping agent's folder replaces that sleeping record, as it replaces a record a paused restore left: the folder then has the new agent only.
- The restore's loading bar counts only the agents it reopens and names the rest: **⏳ Restaurando agentes: 1 de 2 · 2 dormidos / ⏳ Restoring agents: 1 of 2 · 2 sleeping**.
- Sleeping agents have no terminal, so the autopilot never sends them notes or follow-ups, and **Antes de dormir / Bedtime** does not list them.

API: `GET /api/terminals/sleeping` answers `{ agents: [{ id, workspaceId, rel, createdAt, resumable, agent }] }` (`resumable`: its agent can continue what was recorded, a pi session file, a claude or opencode session id, or an agy conversation id; `agent`: the catalog id it was opened with, `null` for the configured `agentCommand`). `POST /api/terminals/sleeping/<id>/wake` answers 202 `{ runId, count }` at once (the run shows in `GET /api/terminals/launches` with `kind: 'wake'`); `POST /api/terminals/sleeping/wake` with `{}` or `{ ws }` wakes every sleeping agent or one workspace's (200 `{ runId: null, count: 0 }` when none sleeps). `DELETE /api/terminals/sleeping/<id>` forgets one (204); every window that watches the inbox stream learns it from the `sleeping` count the stream carries, and re-reads this list when it changes. An unknown id is a 404 `sleeping_unknown`, a malformed one a 400 `sleeping_invalid`. A restore run in `GET /api/terminals/launches` adds `sleeping`: the agents it left asleep, not counted in `total`.

## Opening several agents

Selection mode (☑ on a workspace row, keyboard reachable like the other row buttons) shows a checkbox on each folder row of that workspace; Tab reaches each one and Space marks it. The bar under the workspace row keeps the live count and its actions:

- **Abrir gentle-shell en N / Open gentle-shell in N** opens one agent per marked folder and clears the selection.
- **Guardar como proyectos del workspace / Save as workspace projects** replaces the workspace's saved project set with the marked folders; with none marked and a set saved, the same button reads **Olvidar los proyectos del workspace / Forget the workspace projects**. **Marcar los proyectos guardados / Mark the saved projects** marks the saved set so you can change it and save again.
- **▶ N** on the workspace row opens the saved set with one click, without selection mode.

Before opening, Mirador asks when some of those folders already run gentle-shell: open another one there too, skip them, or cancel. Afterwards a dialog lists the folders that were skipped and why (already open, no longer exists, could not start).

The set is stored as `projects` on the workspace in `config.json`: up to 50 existing folders inside its root (not the root itself), normalized, sorted and kept once; an empty set removes the key, and configs without it load as before (`PATCH /api/workspaces/:id { projects }`, error code `workspace_projects`).

Both actions call `POST /api/terminals/batch` with `{ ws, rels }` (1-50 folders) or `{ ws, saved: true }`, plus optional `reopen`, `cols` and `rows`. The server resolves every folder first: with `rels`, one that is not a folder inside the workspace root refuses the whole request (400 `folder_invalid`) and nothing opens; with `saved`, folders that no longer exist are reported as `missing`. Then it opens the agents one after another, 2 seconds apart (the same pause as reopening agents at startup) and through the launch gate (below), through the same path as a single agent, so the attention bridge, night variables, systemd scopes and open-agent records apply to each. A folder that already runs an agent of that workspace is reported as `already_open` unless `reopen` is true; a folder asked twice opens once. The answer comes when the last agent has started: `{ results: [{ rel, status: 'opened' | 'already_open' | 'missing' | 'failed', terminal? | terminalId? | error? }] }`. When the gate makes the batch wait, the answer comes at that moment instead: the folders still to do are `queued`, it adds a `batchId`, and the batch goes on in the server; `GET /api/terminals/batch/<batchId>` answers `{ results, done }` with what it did since (kept 10 minutes after it ends). A folder the gate gave up on is `low_memory`; one left when Mirador stopped, or when the window went away before the answer, is `cancelled`. The window shows the queued agents as they open, without taking the focus, and lists the ones that did not open at the end. A malformed body is a 400 `batch_invalid`, and `saved` on a workspace without a set a 400 `workspace_projects_empty`.

### Delegating to Mirador

**Delegar / Delegate** on a folder row, or **Delegar a Mirador (N) / Delegate to Mirador (N)** in the selection bar, asks for a short instruction (up to 2000 characters, with a live count) and has **Prender el piloto automático / Switch the autopilot on** checked. Mirador opens gentle-shell in each folder with the instruction as its first message; a folder where gentle-shell is already open gets the instruction as a message instead of a second agent. Checked, an autopilot that is off is switched on until you switch it off. Afterwards a dialog lists every folder: opened, sent to the open agent, no longer exists, or not delegated and why. The autopilot reads the instruction as that agent's task next to the workspace mission, but it never decides anything sensitive because of it: when the instruction mentions something sensitive (pushing, deleting, secrets…), the dialog warns that those questions wait for you, and you can still send it. API: `POST /api/terminals/batch` with `instruction` and `autopilot` (see docs/extending.md). The explanation of the instruction sits under **Cómo funciona / How it works**; the autopilot explanation shows while its box is checked.

## Opening many agents without filling the memory

An agent takes about 1 GB idle and 2-3 GB working, and grows over its first minute while pi and its MCP servers start. Opening 11 at once filled 24 GB of RAM and the swap, and systemd-oomd killed agents and the Mirador window. So agents opened in a row (a multi-open batch, a delegation, the reopening at startup) go through one launch gate in the server (`src/system/memory-gate.ts`):

- **Batches:** 3 agents start, 2 seconds apart; the next one waits until 45 s passed since the last start, so the batch settles. A fixed time is used rather than watching the scopes grow: it works with scopes off and needs no reading per agent, and the memory check below still catches a batch that grew more than usual.
- **Memory:** before each start Mirador reads `MemAvailable` in `/proc/meminfo` and waits, reading it every 2 s, while it is under the reserve: the larger of 2 GiB and 15 % of the RAM.
- **Bounded:** one batch (or the restore) waits for memory 10 minutes in total at most; then its folders left are reported **no se abrió: poca memoria / not opened: low memory** and not opened (at startup, their records stay for the next start, and one log line says so). Stopping Mirador ends every wait at once and nothing starts after it.
- Two batches at once share the gate, first asked first served. A bash terminal always starts at once.
- `GET /api/terminals/launches` answers `{ active, runs }`: each batch or restore in progress (and those ended in the last 10 minutes) with `id` (a batch's `batchId`), `kind`, `total`, `opened`, `queued`, `lowMemory`, `cancelled`, `failed`, `skipped`, and `wait`: `turn` (behind another run), `settle` with `until` (the next batch time), or `memory` with `memAvailable`, `reserveBytes` and `missingBytes`. An ended run adds `notOpened`: the folders (`{ workspaceId, rel }`) it left, for low memory or because it was paused.
- `POST /api/terminals/launches/<id>/cancel` (**Pausar / Pause**) stops what that run has left to start; the agents it opened stay, and the restore keeps the records of the rest for the next start. It answers `{ id, cancelled: true }`, or 404 `launch_unknown` for an unknown or ended run.

### While agents open

A bar under the top bar, in both views, follows every run: **⏳ Restaurando agentes: 9 de 21 · próximo lote en 32 s · memoria libre 6,8 GB / ⏳ Restoring agents: 9 of 21 · next batch in 32 s · 6.8 GB free**, or **esperando memoria libre (falta 1,2 GB) / waiting for free memory (1.2 GB short)** while a batch waits for memory. **Pausar / Pause** stops the launches still to come. At the end it says **Listo: 21 abiertos / Done: 21 open**, or lists the folders not opened (low memory, or left by Pausar to open by hand); × dismisses it. The window reads `GET /api/terminals/launches` every 2 s only while a run is active, and shows the agents the restore opens as tabs without taking the focus.

Until the runs end, what would start one more pi waits, because each one slows the loading down:

- **gentle-shell** on a row, **▶ Abrir N / ▶ Open N**, **Delegar a Mirador / Delegate to Mirador** and **Traer a Mirador / Bring into Mirador** are dimmed, with the reason as tooltip. A single agent asked through `POST /api/terminals` meanwhile (a row's double click or Enter) is refused with 409 `launches_running` rather than queued: the button already says why, and a request held for minutes behind the batches would look like a hang. Batches keep queueing in the gate as above.
- The Claude calls start no pi: the autopilot leaves the decision to you with the reason `Mirador is opening agents` and the judge stores the move as doubtful (`Mirador was opening agents: this move was not reviewed.`). They work again as soon as the runs end; nothing is queued.
- bash, the agents already open, Seguimiento and the daily summary stay free.

As a rule of thumb on a 24 GB machine: about 5-6 agents working at once and 10-12 open in total.

Each value can be changed in `config.json`; a value out of range is left out, logged at startup, and its default applies:

```json
{ "launches": { "batchSize": 3, "settleMs": 45000, "reserveMb": 4096, "maxWaitMs": 600000 } }
```

`batchSize` 1-50, `settleMs` 0-600000, `reserveMb` 0-1048576 (unset: max(2 GiB, 15 % of RAM); 0 never waits for memory), `maxWaitMs` 0-3600000.

**Proposals from memory.** Opened from the tree, **Delegar** fills the instruction with each folder's latest Next Steps from Engram (`GET /api/proposals`), and **Antes de dormir / Before bed** fills each open agent's one note box with its proposal; you edit it or not, and nothing is sent until you press **Dejar la nota** for that agent. Above each agent's note box, **Mejorar con IA / Improve with AI** (marked "1 llamada a Claude") asks Claude once, only when you click, for a short Spanish instruction that continues the folder's next steps, respects the workspace mission, names the project's matching skills and ends with a "Pregunta:" line when something is unclear. It reads the folder's latest session summary and a few recent decisions and fixes, the mission, and the skill names and descriptions of the folder's `.atl/skill-registry.md` (else `~/.agents/skills/*/SKILL.md`), read-only. With several folders in Delegar it reads the first one's memory: one call, one folder's context, and the proposal already holds every folder's Next Steps. Claude's version replaces the text only if you did not edit it while waiting (otherwise it shows as a suggestion you can apply), **Deshacer / Undo** brings your text back, and the sensitive warning checks it like typed text. It uses the night decider's model (`nightModel` or the resource profile's), the same pi gate and a 120 s timeout, and each click is one call charged to the daily **Mejorar con IA** budget (`improveBudget`) and logged as `propose` in the call telemetry. API: `POST /api/proposals/improve` with `{ ws, rel, draft }` (draft up to 2000 characters) answers `{ text }`, or an error code (`proposal_busy`, `proposal_timeout`, `proposal_budget`, `proposal_unavailable`, `proposal_launching`, `proposal_failed`).

**Antes de dormir: pendientes y con nota.** The dialog splits the open agents into two tabs, "Pendientes (N)" and "Con nota (N)". An agent moves to "Con nota" as soon as it has a note of its own for tonight: one not delivered yet, or one delivered since the autopilot turned on. Notes for a whole workspace don't move any agent. "Con nota" shows each note with its time and the Quitar button; removing an agent's last note sends it back to Pendientes. The chosen tab is remembered per window. Each agent is a folded row with its state, its path and "propuesta lista", "nota dejada" or "sin nota"; a row opens by itself while its agent waits for you, and a row you open or close stays that way across refreshes. The explanation of the sheet, the tabs and the capacity sits behind the ⓘ next to the tabs. Notes for agents that are no longer open fold under "Notas de agentes cerrados (N)" at the end of each workspace, one line each until opened, with Quitar always visible.

**Cola de la noche / Night queue.** While the autopilot is on, Mirador lets at most N agents work at once, so one stuck agent never holds the night and the memory never fills up. N is suggested from the machine's memory, about 4.5 GB per working agent (max(1, floor(MemTotal GiB / 4.5)): 5 on a 24 GB machine), and you can change it from 1 to 50 in **Ajustes del turno / Shift settings** ("Agentes trabajando a la vez"). Only an agent that is working holds a slot; one that finished its turn, waits for your decision, or has not reported anything (its state is unknown) holds none. A note for an agent without a slot, and every automatic follow-up when it is due, wait in a queue, first in first out; when a slot frees the next one gets its note (all its notes, in order) and starts. The agent just started keeps that slot until it reports working or ends its turn. A note for a whole workspace counts as delivered only once every agent got it during the same activation; if the autopilot turns off (or Mirador stops) halfway, it stays waiting and the next activation gives it to the agents that did not get it yet (after a restart, the ones that got it receive it again). The next start also waits while free memory is below the launch reserve (max(2 GiB, 15 % of RAM), config `launches.reserveMb`). The strip shows "Trabajando 5 de 5 · 3 en cola" (and "esperando memoria libre"); **Antes de dormir** shows "Para tus 24 GB: hasta 5 agentes trabajando a la vez" behind the ⓘ next to its tabs, and under each note where it would start ("Al activarse el piloto espera en la cola: n.º 2"), or, while on, its place in the queue. Turning the autopilot off empties the queue: the notes stay waiting for the next on and the queued follow-ups are dropped. What you do yourself is never queued: typing, **Delegar**, a delegated task and the questions Mirador answers. API: `GET /api/night/queue`, `PUT /api/night/queue { slots: 1-50 | null }`; `GET /api/night` adds `queue` while the autopilot is on.

**Proposals from the latest memory.** Every time "Antes de dormir" opens, it asks the memory again for each pending agent's proposal. An empty box or a proposal you haven't edited is replaced by the newer one; a text you typed or edited stays. The note box names its source ("Nota (propuesta de la memoria, 02/11 21:40)", in the configured time zone) and warns, without blocking anything, when it may be outdated: "Hubo actividad después de este resumen (última memoria 23:10): revisa que no esté hecho" when the project saved memories after that summary, and "Ya le enviaste una nota o delegación a las 22:05 después de este resumen" when a note or delegation already reached that folder's agent. `GET /api/proposals` returns these per folder as `summaryAt`, `latestMemoryAt`, `newerMemories` and `lastSentAt`. `lastSentAt` comes from the night log's delivered notes and delegations of the last 7 days and from notes waiting for an open agent.

## One systemd scope per terminal

When memory runs out, systemd-oomd kills a whole cgroup: on a swap kill it picks the cgroup using the most swap, and it ignores `ManagedOOMPreference=avoid` for cgroups owned by your user (see `man systemd.resource-control`). Started from a terminal, Mirador and every agent used to share that terminal's cgroup, so one kill took them all. Now each one gets its own transient systemd user scope, and a kill takes one terminal:

- `mirador` starts the server in `mirador-server-<pid>.scope`.
- Each terminal runs in `mirador-agent-<terminal id>.scope` or `mirador-shell-<terminal id>.scope`.

Both use `systemd-run --user --scope --collect --quiet --expand-environment=no`. It runs the command in place, so the process keeps its pid, folder, variables and exit code or signal (an agent killed by a signal still reopens at the next start), and the scope goes away when the process exits. No memory limit is set.

When the server stops (`mirador stop`, SIGINT or SIGTERM) it hangs up every terminal as before and then runs `systemctl --user stop` on each terminal's scope, which sends SIGTERM to everything still running in it and SIGKILL after the user manager's stop timeout (`systemctl --user show -p DefaultTimeoutStopUSec`). An agent that shuts down slowly on the hangup, or a server it started, cannot outlive Mirador and run next to the agent reopened at the next start. Closing one terminal with × does the same for its scope, without making the window wait for the stop.

At startup the launcher and the server each check once that `systemd-run --user --scope` works (no user manager or session bus, no systemd, or a `systemd-run` without `--expand-environment` fails the check). If it does not, they start the server and the terminals as before, without scopes. The server logs one line with the result: `mirador: terminal scopes on: …` or `mirador: terminal scopes off: …` (see `mirador logs`). To turn scopes off, set `MIRADOR_SCOPES=0` in the environment, which covers the server and the terminals, or set `"scopes": false` in `config.json`, which covers the terminals only.

A terminal stopped by a signal says so in its tab and pane (**detenido (señal 9) / stopped (signal 9)**) instead of an exit code. When the user journal shows that its scope was stopped because memory ran out (systemd-oomd or the kernel; the unit result `oom-kill`), it says **detenido: sin memoria / stopped: out of memory**, and `GET /api/terminals` adds `oomKilled: true`. Mirador looks that line up for a couple of seconds after the kill; without it, it only names the signal.

To see the scopes:

```sh
systemctl --user list-units 'mirador-*'
```

## MCP servers per project

Every gentle-shell agent starts all the MCP servers it knows, and each one takes memory in every agent (measured once with an idle agent: markitdown ~180 MB, azure ~230 MB, codegraph ~180 MB, context7 ~110 MB, bicep ~85 MB). **MCP** on a folder row (not on workspace rows) lists the servers agents in that folder would start, with a switch each, where it comes from (gentle-shell or the project) and its estimated memory, and adds up the saving per agent of the servers turned off. Each server's description opens from the chevron at the end of its row (or shows as a tooltip on its name). The git note, the memory-estimate note and when the change applies are folded under **Cómo funciona / How it works**; trust and unreadable-config warnings stay on screen. **Guardar servidores / Save servers** applies to agents opened or woken from then on; agents already open keep their servers.

- **What it reads, never writes:** gentle-shell's agent dir (`gentleShellAgentDir` in `config.json`, else `GENTLE_SHELL_HOME`, else `~/.gentle-shell/agent`): its `mcp.json` for the servers, and `trust.json` and `settings.json` to tell whether pi trusts the folder. A server the user file turns off (`enabled: false`) shows as off for every project and is not changed here.
- **What it writes:** only the folder's `.pi/mcp.json`, the file pi's own `/mcp` "Disable in this project" writes. Turning a server off adds `"enabled": false` to its entry, or a bare `{ "enabled": false }` override; turning it back on removes that again. Every other key and server stays as it was (a server the project declares keeps all its fields). The file is written to a temp file and renamed; `.pi/` is created only when there is something to save. A file that is not valid JSON, or a `.pi` or `.pi/mcp.json` that is a symlink, is refused and left untouched.
- **Git:** when the file is untracked and not ignored, Mirador appends its path (`/.pi/mcp.json`, or `/<sub>/.pi/mcp.json` for a folder inside a repo) to the repo's `.git/info/exclude` once, so it never shows in `git status`. A tracked file is not excluded: the dialog's **Cómo funciona** says the change will show in git, and saving confirms it.
- **Trust:** pi reads `.pi/mcp.json` only in projects it trusts. Mirador takes the nearest saved decision for the folder or a parent in `trust.json`, else `defaultProjectTrust` (`always` or `never`); otherwise, or when an extension may decide, it says it cannot tell. It never grants trust nor starts agents with `-a`: when the project is not trusted, or it cannot tell, the dialog says to open `/mcp` in an agent of that project and trust it.

API: `GET /api/mcp?ws=&rel=` and `PUT /api/mcp` with `{ ws, rel, disabled: [names] }` (see docs/extending.md).
