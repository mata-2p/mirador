# Extending Mirador

How a feature plugs into Mirador without editing other features. Wave 2 (W3 overview, W4 inbox, W5 file editor) runs in parallel worktrees: put your code in **new files** and touch shared files only on the lines reserved for you below. Each shared list has a marker per unit (`// W4 inbox`, `<!-- W4 inbox -->`); add your line **directly under your own marker** and leave the blank line after it, so the three branches merge without conflicts. The line numbers below are from branch `wt/workspaces`; the marker comment is the anchor if they shift.

## 2. Server: a route module

```ts
// src/http/routes/inbox.ts
import type { RouteModule } from '../context.ts';
import { HttpError, readJson, sendJson, sendNoContent } from '../respond.ts';

export const inboxRoutes: RouteModule = (ctx) => [
  { method: 'GET', path: '/api/inbox', handler: ({ res }) => sendJson(res, 200, []) },
  { method: 'DELETE', path: '/api/inbox/:id', handler: ({ res, params }) => { /* params.id is decoded */ sendNoContent(res); } },
];
```

- `RouteModule = (ctx: AppContext) => Route[] | Promise<Route[]>` runs once at startup; do async setup (sockets, watchers) there. `Route = { method: 'GET'|'POST'|'PUT'|'PATCH'|'DELETE', path, handler({ req, res, url, params }) }`; `:name` matches one path segment. A duplicate method+path throws at startup.
- Before any route runs, `server.ts` has already checked the Host header, the session token and, for every non-GET, the `Origin`. Do not re-implement or skip them; do not add routes outside `/api/`.
- `src/http/respond.ts`: `sendJson(res, status, body)`, `sendNoContent(res)`, `readJson(req)` (JSON object only, max 64 KiB counted in bytes and decoded once, else 400/413), `HttpError(status, message, code?)`, `SECURITY_HEADERS` (put them on any non-JSON response you write yourself).
- Errors: throw `HttpError` with a stable `code`; the response is `{ error, code }` and the UI shows `t('error.<code>')` when your dictionary defines it. Already mapped: `InvalidFolderError` → 400 `folder_invalid`, `UnknownWorkspaceError` → 404 `workspace_not_found`, `InvalidWorkspaceError` → 400 with its code (`workspace_config` when config.json holds workspaces Mirador could not read: every workspace change is refused), `EngramUnavailableError` → 503.

`AppContext` (`src/http/context.ts`):

| Member | Use |
|---|---|
| `config` | settings: `port`, `engramUrl`, `agentCommand`, `shell`, `ignore`, `timeZone` (no workspaces) |
| `workspaces` | `WorkspaceStore`: `list()`, `get(id)`, `add(input)`, `update(id, patch)`, `remove(id)`, `resolve(id, rel)`; `get(id)?.mission` is the workspace's Markdown mission (`undefined` when unset), changed with `update(id, { mission })`, which rejects invalid input with code `workspace_mission` |
| `resolveFolder(ws, rel)` | **the only way to turn client input into a folder path**: `{ workspace, path, rel }`; unknown ws → 404, outside its root → 400 |
| `terminals` | `TerminalRegistry`: `list()`, `get(id)`, `create(…)`, `write`, `resize`, `close`, `addEnvProvider(fn)`, `subscribe(fn)` |
| `engram` | `EngramClient`: `projectFor(cwd)`, `projects({ timeoutMs? })`, `observations(project)`, `allObservations()`, `sessions(project)`. Lists Engram answers as `null` or not as a list read as empty; a non-JSON answer is `EngramUnavailableError`. `allObservations()` is shared by every route for 3 s: never mutate its entries |
| `today()`, `parseDate(value)` | YYYY-MM-DD in `config.timeZone`; a bad `date` is a 400 |
| `onShutdown(fn)` | runs on SIGINT/SIGTERM before terminals close |

Terminal hooks (`src/terminals/registry.ts`):

- `ctx.terminals.addEnvProvider((info) => ({ HERDR_PANE_ID: info.id, … }))` adds variables to every terminal created afterwards; Mirador's `TERM`, `COLORTERM`, `TERM_PROGRAM` and `MIRADOR_AGENT_COMMAND` win. Do not pass secrets: the agent and everything it runs can read them.
- `ctx.terminals.subscribe((event) => …)` → `{ type: 'created' | 'exited' | 'closed', info }`; returns an unsubscribe function. A throwing listener is logged, not fatal.
- Sockets or files a feature creates belong under `runtimeDir()` (`src/config.ts`, mode 0700, per user).

## 3. UI: a feature module

```js
// public/features/inbox.js
import { el, on, slot, state, t } from '/core.js';
import { activateTerminal } from '/terminals.js';

export async function init() {
  const host = slot('inbox');
  const render = () => host.replaceChildren(/* el(...) nodes */);
  on('terminals', render);
  on('language', render);
  render();
}
```

`init()` runs once, in `FEATURES` order, after sign-in, `GET /api/bootstrap` (the config and the workspaces in one request), and after the terminals reattached.

Top bar and settings sheet: the brand, the `topbar` slot, a **Piloto automático / Autopilot** chip shown only while the autopilot is on, the free-memory figure (`#topbar-memory`, filled by `public/features/resources.js`) and one **Ajustes / Settings** button that opens `#settings-sheet`. `public/features/settings.js` builds the sheet's rows from `public/settings-model.js` (`SETTINGS_ROWS`, `pressedChoices`, `nightSwitchView`, `sheetCloses`, tested in `test/settings-model.test.ts`): the night shift switch (`role="switch"`, `toggleNight()` from `public/features/night.js`), terminals (`data-layout`, wired by `public/terminals.js`), theme (`data-theme-choice`, `setTheme`) and language (`data-lang`, wired by `public/app.js`). `app.js` calls `mountSettings()` before it wires those buttons. Esc or a click outside closes the sheet and returns the focus to the button; a dialog the sheet opened keeps it open. A top-bar element marked `data-development-only` is hidden while Tracking shows. Strings in `public/i18n/settings.js`, styles in `public/styles/settings.css`.

Responsive layout: `public/features/drawers.js` marks `#layout` with `drawer-panel` under 1280 px and `drawer-sidebar` too under 960 px (`drawerSides` in `public/drawer-model.js`, tested in `test/drawer-model.test.ts`). A drawer side leaves the grid; its topbar button (`.side-show`, the `i-sidebar` and `i-panel` icon buttons, shown by `styles.css` while a side is hidden or a drawer) slides it in over the terminals (`data-open` on `#layout`, one at a time, `nextOpen`). One click on the other drawer's button swaps them, and a click on the open drawer's own button closes it. An open drawer is modal: `inertRegions` lists what gets the `inert` attribute (everything behind it except the two drawer buttons; the `modals` slot stays live), and Tab and Shift+Tab wrap inside it (`trapTab`). Its `.side-hide`, the `.drawer-scrim` or Esc close it and give the focus back to the button that opened it (`focusTarget`); growing the window past the breakpoint closes it and clears `inert`. `columns.js` `wireSide` ignores those clicks while the side is a drawer, so the `sidebarOpen` and `panelOpen` prefs keep the wide-window state; in a wide window the same topbar button brings a hidden column back, and `clamp()` counts a hidden side or a drawer as no width. In the grid layout, a terminals area of 640 px or less stacks the panes in one scrolling column (`stacksPanes`, `gridTracks(groups, collapsed, areaWidth)` in `public/terminal-groups.js`; `#panes[data-stacked]`).

Text: put every string in `public/i18n/<feature>.js` (`export default { en: {...}, es: {...} }`), prefix keys with your feature (`inbox.title`), and give both languages the same keys and placeholders; `test/i18n.test.ts` fails otherwise, and `mergeDictionaries` throws if two features define the same key. With no saved choice the UI follows the browser's language, Spanish for `es-*` and English otherwise (`pickLanguage` in `public/i18n.js`). Mark static HTML with `data-i18n`, `data-i18n-title`, `data-i18n-label` and call `applyStaticText(node)`.

## 4. Data shapes

```ts
Workspace    = { id: string, name: string, root: string, folders: string[], expanded: string[] }  // folders/expanded relative to root
FolderNode   = { name, rel, path, hasChildren: boolean, isRepo: boolean, hasMemory: boolean | null }  // GET /api/tree
TerminalInfo = { id, workspaceId, rel, cwd, title, kind: 'agent' | 'shell', status: 'running' | 'exited', exitCode?, createdAt }
Selection    = { ws: string, rel: string } | null   // rel '' = the workspace root
```

| API | Answer |
|---|---|
| `GET /api/config` | `{ agentCommand, timeZone, today, mode }`. `mode` is `'gentle-deck'` (the full mode) or `'plain'`: the config key `mode` (`"auto"`, the default, `"gentle-deck"` or `"plain"`; anything else is auto, with a warning at startup) resolved per request by `resolveMode` in `src/mode.ts`; auto is the full mode when gentle-ai's `state.json` exists or `gentle-shell` is on `PATH`. In plain the UI hides the gentle extras, the help guide's entries about them included (`helpSections`). The app is "Mirador" in every mode: the name lives only in `BRAND` (`public/mode-model.js`), so a message that names the app writes `{brand}`, which `translate` fills with it (a caller may pass `brand: brandOf(state.config)`). No i18n message writes the name out, and none says gentle-deck (`test/brand-visible-name.test.ts`) |
| `GET /api/bootstrap` | `{ config, workspaces }`: the bodies of `GET /api/config` and `GET /api/workspaces`, in one request; the UI's start-up call (`public/app.js`) |
| `GET /api/agents` | `{ agents: { id, label, command, configured, attention, resume }[] }`: the configured `agentCommand` first (`id: null` outside the catalog), then gentle-ai's `installed_agents` that are in the catalog and on `PATH` |
| `GET /api/workspaces` | `Workspace[]` |
| `POST /api/workspaces` `{ root, name? }` | 201 `Workspace` (name defaults to the folder name) |
| `PATCH /api/workspaces/:id` `{ name?, folders?, expanded? }` | 200 `Workspace`; other fields → 400 `unknown_field` |
| `DELETE /api/workspaces/:id` | 204 (config only, never the disk) |
| `GET /api/tree?ws=&rel=[&all=1]` | `FolderNode[]`; at rel `''` the chosen folders, or all with `all=1` |
| `GET/POST /api/terminals`, `DELETE /api/terminals/:id` | `TerminalInfo[]` / 201 `TerminalInfo` (body `{ ws, rel, kind, cols, rows, agent? }`) / 204. `agent` (agent terminals only) is the id of an agent `GET /api/agents` offers, else 400 `agent_not_offered`; the terminal and its `open-agents.json` record keep it (`TerminalInfo.agent`) and a restore reopens that agent, continuing its session only with a verified resume (pi; claude-code with the session id its hooks reported; opencode with the session id its plugin reported; antigravity with the conversation id its hooks reported). The configured agent's id, or no id, starts the configured `agentCommand` with its bridge as before; any other agent runs its catalog launch line without it, plus its own bridge when it has one (claude-code: `--settings <file>`; opencode: `--standalone` and `OPENCODE_CONFIG_CONTENT`; antigravity: `--add-dir <folder>`). In the UI, "Start <agent>" items in a row's "Más" menu (`public/features/agent-picker.js`) appear only while more than one agent is offered |
| `GET /api/summary?ws=&rel=&date=` | daily summary of that folder, with `truncated` |
| `GET /api/activity?date=` | activity across all Engram projects, with `truncated` |

## 5. Notes per unit

- **W3 overview** (built: `src/http/routes/overview.ts`, `src/memory/overview.ts`, `public/features/overview.js`, `public/i18n/overview.js`, `public/styles/overview.css`).
  - `GET /api/overview?ws=&date=` → `{ workspace: { id, name }, date, truncated, summary: { folders, activeFolders, memories, sessions, headlines: [{ title, type, at, folder, rel }] }, rows: FolderRow[] }`. Folders are the ones the sidebar shows (chosen, or every first-level folder); the root gets a row (`rel: ''`) only when Engram holds memory saved in the root itself. Two Engram reads: `GET /projects` and one all-projects window; `folderProjects(listing)` maps folders to projects by the same rule as `memoryLookup`.
  - `GET /api/overview/folder?ws=&rel=&date=` → `{ cwd, projects, truncated, row: FolderRow }`, with the folder resolved to its project as `/api/summary` does (`projectFor`, else `projectsUnder` for a container).
  - `FolderRow = { name, rel, path, isRepo, projects, hasMemory, lastAt, lastDay, beyondWindow, leftOff: { summary: { at, goal, accomplished, nextSteps } | null, memory: { title, type, at } | null }, day: { memories, sessions, headlines } }`. `lastAt` is the latest memory on any day; `beyondWindow` means Engram holds memory for the folder but none lies in the window read. "Sessions" are the sessions that saved memories that day (distinct `session_id`).
  - UI: a `Summary` panel view (`id: 'overview'`) for a workspace root and a `Where it left off` view (`id: 'leftoff'`) for a folder, between "Te esperan" and "Día" in the panel segment. A folder opens on `leftoff` unless this window chose another view for folders (`prefs` key `panelViews`, versioned by `PANEL_VIEWS_VERSION` in `public/features/summary-model.js`). The date nav belongs to "Día" (`id: 'daily'`), which keeps the stats, the latest session summary, the memory groups and the glossary.
- **W4 inbox** (built). Server: `src/http/routes/inbox.ts` (`GET /api/inbox` → `{ items }`, `GET /api/inbox/stream` → NDJSON `{ items }` on every change (a report expiring at the end of its `ttlMs` is a change too), `{}` heartbeat every 25 s, `POST /api/inbox/:id/seen` → 204, the finished turn of that terminal was seen) over `src/attention/` (`store.ts` state, validation and `isTyping`; per pane, `mirador:attention` and `gentle:activity` always have a slot and other sources at most two, and, since both reporters number reports from the clock, a `seq` more than 60 s past the clock is refused and a stored `seq` more than 1 s past it is replaced by the next report at the clock, `herdr.ts` env provider and `<runtime>/herdr/` folder, `socket.ts` the 0700/0600 Unix socket, `agent-args.ts` which agent commands get `-e <bridge>`, `--settings <file>`, `--standalone` or `--add-dir <folder>` and which terminals get a bridge variable (`bridgeEnvProvider`), `gentle-shell-bridge.ts` the pi extension, `claude-hooks.ts` Claude Code's settings file, `opencode-plugin.ts` opencode's plugin folder, `agy-hooks.ts` agy's hook folder) and `bin/herdr-shim`. Registry hooks it uses: `addEnvProvider`, `subscribe`, `addAgentArgs(args)` (quoted words appended to agent commands), `addChosenAgentArgs(agent, args)` (the same for a chosen agent run by its own command line) and `onInput((id, data) => …)`.
- **Claude Code bridge**. Mirador never edits `~/.claude` or a project's `.claude`: it writes `<runtime>/herdr/claude-settings.json` (0600) and starts claude with `--settings <that file>`, as the configured agent and as a chosen one (not with `attentionBridge: false`); Claude merges those hooks with the user's own. Each hook (`UserPromptSubmit`, `PostToolUse`, `Notification`, `Stop`) runs `bin/claude-hook` with Mirador's node, which sends one `mirador:attention` report on the herdr socket: a prompt or a finished tool call is working (clears `blocked`, `prompt`, `finished`), a `Notification` that waits for an answer (`permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `agent_needs_input`, or no type) is waiting (`prompt=<message>`), `Stop` is finished (`finished=<turn>`); idle reminders and other notices change nothing. Each report also carries `session=<session_id>`: `AttentionStore.onSession` hands it to `OpenAgents.recordSessionId`, the record keeps it as `session` (a `SESSION_ID`: a letter or digit first, then up to 127 letters, digits, `_` or `-`), and a restore or wake runs `claude --settings <file> --resume <id>`; without one, claude starts fresh. Interrupting a turn with Esc fires no `Stop`, so it stays working until the next event. `GET /api/terminals/sleeping` adds `agent` (the catalog id, `null` for the configured `agentCommand`), and `resumable` is true only when that agent can resume what was recorded (a pi session file never resumes claude). `AttentionItem = { terminalId, workspaceId, rel, title, kind: 'blocked' | 'prompt' | 'finished', label, detail, since, activity }`. UI: `public/features/inbox.js` renders the `inbox` slot, which the panel shows in its "Te esperan (N)" view (answers, then finished; the active terminal of a visible window is left out; N counts the items that need an answer), emits `inbox` with the items, sets the window title count, calls `markWaiting(waiting, finished)` from `/terminals.js` (`data-waiting` / `data-finished` on tabs and panes) and listens to the `activate` event (`/terminals.js` emits it with the id from `activateTerminal`). When a label names a file (`src/app.ts`, `.env.example`), the entry offers **Open** and emits `files:open` with `{ ws, rel, path }` (`path` relative to that folder) for W5.
- **opencode bridge** (opencode 2). opencode runs plugins in its server, and by default every `opencode` shares one background server, so Mirador never edits `~/.config/opencode` or a project's `.opencode`: it copies `bin/opencode-plugin.js` to `<runtime>/herdr/opencode-plugin/index.js` (folder 0700, files 0600, with a `package.json` that makes it an ES module) and starts opencode with `--standalone` (a private server for that terminal, which inherits its environment) and `OPENCODE_CONFIG_CONTENT={"plugins":["<that folder>"]}` (`bridgeEnvProvider`, opencode agent terminals only; not with `attentionBridge: false`). opencode merges that layer with the user's config, and plugin lists add up. The plugin follows the server's events and sends one `mirador:attention` report per event on the herdr socket: a root session's `session.execution.started` is working, `permission.asked` (`prompt=<message>`, else the action) and `form.created` (the question tool, `prompt=<title>`) are waiting, `permission.replied` and `form.replied`/`form.cancelled` working again, and `session.execution.succeeded`, `failed` or an `interrupted` by the user or for inactivity finished (a `superseded` or `shutdown` interrupt changes nothing). Subagent sessions (`session.created` with a `parentID`) can wait but never finish the turn or name the session. Each root report carries `session=<sessionID>` (`ses_…`, a `SESSION_ID`), recorded like claude's, and a restore or wake runs `opencode --standalone --session <id>`. Known limits: an `OPENCODE_CONFIG_CONTENT` exported in `~/.bashrc` replaces Mirador's (no attention then); with several tabs the record keeps the session that reported last; opencode 1 (other plugin API, no `--standalone`) is not supported.
- **agy bridge** (Antigravity CLI, catalog id `antigravity`). agy reads hooks from `~/.gemini/config/hooks.json`, from plugins, and from `.agents/hooks.json` in each workspace folder, which is the folder it starts in plus each one added with `--add-dir` ([hooks](https://antigravity.google/docs/hooks), [customization discovery](https://antigravity.google/docs/customization-discovery)). agy has no settings flag or variable for an extra config, so Mirador never edits `~/.gemini` or a project's `.agents`. It writes `<runtime>/herdr/agy-workspace/.agents/hooks.json` (folders 0700, file 0600) and starts agy with `--add-dir <runtime>/herdr/agy-workspace`, as the configured agent and as a chosen one (not with `attentionBridge: false`). Hooks from every location run, so the user's own still do. Each hook runs `bin/agy-hook <event>` with Mirador's node, because agy's payload does not name its event. The script answers agy on stdout (`{"decision":"allow"}` for `PreToolUse`, which defers to the next hook or agy's own policy, `{"decision":"stop"}` for `Stop`, whose `decision` is required and lets agy stop unless it is `"continue"`, and `{}` otherwise), always exits 0, and sends one `mirador:attention` report on the herdr socket:
  - `PreInvocation` (before each model call) is working;
  - `PreToolUse` for `ask_question` or `ask_permission` (the hook's matcher) is waiting, with `prompt=<the first question>`, else the permission's `Reason`;
  - `Stop` is finished.

  `SessionStart` is not hooked: it would mark an agent that has not started a turn as working, and the `PreInvocation` that follows names the same conversation. Each report carries `session=<conversationId>` (a UUID, a `SESSION_ID`), recorded like claude's. A restore or wake runs `agy --add-dir <folder> --conversation <id>` ([resume](https://antigravity.google/docs/cli/commands/resume)). `-c` is not used, because it takes the folder's latest conversation, which another agy terminal in the same folder may own.

  Known limits, none of them run against the real binary:
  - The recorded id goes stale after `/resume`, `/fork` or `/clear` until the next model call reports the new one. Closing agy right after one of them resumes the old conversation.
  - agy shows the hook folder to the agent as a second workspace folder (it is in `workspacePaths`), and the agent could read or edit `hooks.json`.
  - If agy asks to trust a new workspace folder, the hook folder may be asked about too. Whether hooks of an untrusted folder load is not documented.
  - A tool permission prompt from agy's own policy (a `run_command` approval) has no hook, so it is not seen as waiting. Only the question and permission tools are.
  - Whether subagent conversations fire these hooks is not documented. If they do, a subagent's `Stop` can show a turn as finished early, and its conversation id can replace the main one.
- **kimi, no bridge** (Kimi Code CLI, npm `@moonshot-ai/kimi-code`, catalog id `kimi`). kimi has `[[hooks]]` (`TurnStarted`, `PermissionRequest`, `Stop`, `Interrupt` and more, each payload with `session_id`), but it reads them only from `$KIMI_CODE_HOME/config.toml` and from installed plugins: "Hook rules live only in your user-level `config.toml` and in local plugins" ([hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks)). There is no config flag, no project-level config ([overrides](https://moonshotai.github.io/kimi-code/en/configuration/overrides)), and no environment variable sets hooks (the `hooks` config section registers none: `packages/agent-core-v2/src/features/externalHooks/configSection.ts` in MoonshotAI/kimi-code at `7490d07`, where `externalHooksRunnerService.ts` joins only the config's hooks and the enabled plugins'). `KIMI_CODE_HOME` moves the config together with the sessions and OAuth credentials ([environment variables](https://moonshotai.github.io/kimi-code/en/configuration/env-vars)), so pointing it at a folder of Mirador's would drop the user's own settings and login. Installing a plugin writes `$KIMI_CODE_HOME/plugins/installed.json` and applies to every kimi ([plugins](https://moonshotai.github.io/kimi-code/en/customization/plugins)). So kimi stays launch-only, the fallback: Mirador adds no words and no variables, configured or chosen, and writes no kimi file. Without hooks nothing reports a session id, so a restore or wake starts `kimi` fresh, even when a record carries a `session`. `kimi --session <id>` (`-S`, hidden alias `-r`) is not used, and neither is `-c` (`--continue`), which takes the folder's latest session ([kimi command](https://moonshotai.github.io/kimi-code/en/reference/kimi-command)). The legacy Python kimi-cli (PyPI `kimi-cli`, archived) had `--config-file`, but that replaces the user's config and the package is no longer supported. Known limits: kimi never shows in the inbox and its state stays unknown, so a restart always reopens it; it never idle-sleeps (nothing to resume). Never run against a real kimi.
- **W5 file editor.** `resolveInsideRoot` only accepts folders. Add a file guard next to it in `src/folders/tree.ts` (realpath of the file inside the workspace root, regular file, size cap) with tests, and resolve the folder part with `ctx.resolveFolder`. `readJson` caps bodies at 64 KiB; add a limit option there if you need more. Show file text with `textContent` or `<textarea>.value`, never as HTML.

| API | Answer |

## Night shift

Server: `src/http/routes/night.ts` over `src/night/` (`channel.ts` the socket, `policy.ts` what may be decided, `service.ts` the flow, `log.ts` the audit log, `decider.ts` the model; the contract is `protocol.ts`).

| API | Answer |
|---|---|
| `GET /api/night` | `{ active, available, since, source, until, connectedTerminals: string[], pending: PendingItem[] }`; `source` is who turned the autopilot on (`'manual'` or `'schedule'`, `null` while off); `until` is when a manual on turns itself off (ISO) or `null`; `PendingItem = { id, time, kind, terminalId, workspaceId, rel, tool, summary, rule, reason }`; while the autopilot is on it adds `queue` (the night queue's summary, below) |

| `PUT /api/night/queue` `{ slots: 1-50 \| null }` | the same summary, once saved in `night/queue.json` (0600); `null` goes back to the suggested N. 400 `night_queue` for anything else. |

Turning it off passes the questions in flight. |
| `POST /api/night/delegate/:terminalId` | 202 `{ id }`, the id of the log record; 404 `night_terminal` |
| `GET /api/night/activations?limit=` | `{ activations: AutopilotChange[] }`, latest first (default 100); each `{ time, from, to, cause, reason?, saved? }` is one autopilot on, off, take-over, handover, until change or shutdown (`cause`: `user`, listed for older lines that hold the legacy value `LEGACY_USER_VALUES.cause` too, `delegation`, `until`, `handover`, `window-start`, `window-end`, `shutdown`, `restart-resume`, `restart-deferred`, `restart-dropped`). 400 `night_limit`. |
| `GET /api/night/log?since=&limit=` | `{ records: NightRecord[] }`, oldest first. `since` is an ISO time or epoch ms (default: the last 24 h); `limit` is 1-1000 (default 500). 400 `night_since` / `night_limit`. |

- **Socket:** `<runtimeDir>/night/socket` (folder 0700, socket 0600). Agent terminals get `MIRADOR_NIGHT_SOCKET` and their own `MIRADOR_NIGHT_TOKEN`. The first line must be `hello` with that token, within 5 s. Lines are JSON, at most 64 KiB each, at most 20 questions a minute per connection.
- **Bridge:** the gentle-shell bridge forwards ask_user_choice / ask_user_question (labels and descriptions only, never option values) and blocks the call only on `decided`. Anything else, including errors and timeouts, opens the dialog.
- **Dialogs**: the bridge also wraps pi's `ctx.ui.select` and `ctx.ui.confirm` (re-wrapped at every `session_start`, never twice). The dialog opens in the terminal as always and is sent as `{ "type": "dialog", "requestId", "dialog": { terminalId, kind: 'select'|'confirm', title, message, options } }` (confirm: options `Yes`, `No`; at most 20 options and 16 000 characters of title, message and labels together, with the line within 64 KiB). A bigger one is sent as a notice, `notice: true` with its kind and title cut to 300 characters and no message or options, so nothing is ever cut: Mirador holds it like any dialog and its end is told the same way, but it cannot be answered from Telegram (the bridge ignores a `chosen` for it and leaves the terminal dialog untouched). While the autopilot and «Responder desde Telegram» are on, Mirador answers `held`; never the decider. The user's answer from Telegram comes back as `{ "type": "chosen", "requestId", "index" }`: the bridge closes the terminal dialog, returns that option (confirm: Yes → `true`, No → `false`) and answers `{ "type": "took", "requestId" }`; only then does Mirador end the hold `answered` and log the answer (10 s without `took` or `released`, from a bridge that predates `took`, count as `took`). A `chosen` the bridge cannot apply (an index out of range) is ignored and it keeps waiting. If the terminal answers first (or Esc, an abort, a timeout), even in the same instant as a Telegram «Confirmar», the bridge sends `released`: Mirador ends the hold `terminal` with no record and the Telegram message is edited to say so. When ctx.ui cannot be wrapped, dialogs stay as they are and pi shows one warning. `input`, `editor` and `custom` dialogs are not forwarded.
- **Log:** `$XDG_STATE_HOME/mirador/night/decisions.jsonl` (0700/0600), rotated at 5 MiB into `decisions.1.jsonl`.
- **Never decided:** multi-select questions, free-text-only questions, 0 or more than 4 questions, fewer than 2 or more than 4 options, and anything that mentions .env files, secrets, tokens, passwords, credentials, keys, certificates, SSH, secret config under ~, permissions, sudo, consent, deleting or force-pushing, production, deploys, releases or payments (English or Spanish). The decider adds its own deferrals (push, merge, deploy, delete, secrets, prod, payments, review bypass) and defers below confidence 0.7.
- **Decider:** pi print mode through the Claude bridge (the pi runner above), model `nightModel` (default `claude-sonnet-5-5`), mission and terminal text on stdin as delimited data. The owner's past corrections are read from Engram project `mirador-night`, topic `night-feedback/<workspaceId>`.
- **Owner's name:** config `ownerName` (`src/config.ts` `ownerNameFrom`; unset or not valid: `DEFAULT_OWNER_NAME`, "the user") is the only source of the name in the decider's, the judge's and «Mejorar con IA»'s prompts (`buildDecisionPrompt`/`buildFollowUpPrompt` read `NightContext.ownerName`; `buildJudgePrompt` and `buildImprovePrompt` take it as their last argument; `createJudge` and `createImprover` take `ownerName`, a value or a function), in what agents receive (`noteText`, `taskText`, `decidedReason`, `followUpText`, and the idle-sleep `sleepNote` through `IdleSleep` option `ownerName`), in the policy and night service reasons (`checkQuestion`'s third argument, `NightService` option `ownerName`) and in the feedback memory. `JUDGE_SYSTEM_PROMPT` and `IMPROVE_SYSTEM_PROMPT` are the default-config prompts. `test/owner-name.test.ts` checks that no prompt names the author with the default config. Prompt versions: `night-decider-v4`, `night-judge-v3`, `proposal-improve-v2`.
- The attention store reaches the night service through `provideNightAttention(ctx.terminals, store)` in `src/http/routes/inbox.ts`.

### Automatic follow-up

When an agent's turn ends, the bridge sends Mirador the turn's final assistant text (at most 32 KiB, keeping the end). While the night shift is on, Mirador waits 20 s and, if the agent is still idle, the user has not typed in it and no newer turn arrived, asks the decider for a follow-up with that whole message. If the message ends with a question and a recommendation the workspace mission covers, Mirador tells the agent to proceed with the recommended option; otherwise it defers and the item stays pending. Limits: 10 automatic follow-ups per terminal per night, and none after 2 deferrals in a row until the user types in that terminal or the night shift is turned on again. A closing question about sensitive material (push, deploy, delete, secrets, production, payments…) is never decided. Log records use kind `auto-follow-up`. Socket line (bridge → Mirador): `{ "type": "finished", "turnId": "<id>", "text": "<final text>" }`. `NightService.onActiveChange(listener: (active, since, cause) => void): () => void` fires when the autopilot turns on or off.

### Autopilot

The night service is one **Piloto automático / Autopilot**; the night shift is its schedule. Routes, files, Engram project and types keep their `night` names. Who switched it on decides who switches it off: the scheduler turns off at a window end only an on it made; a manual on survives window starts and ends. A manual `until` that passes inside a running window (enabled, not turned off by the user) hands the autopilot to the schedule (`source` becomes `'schedule'`, same activation, no off) and the window end turns it off; outside a window, or inside one the user turned off, it turns off as the user's off. A manual on is saved in `$XDG_STATE_HOME/mirador/night/autopilot.json` (`{ manual: { since, until } | null }`, 0600) and resumed after a restart while its `until` is ahead. `NightService.onActiveChange(listener: (active, since, cause) => void)`: `cause` is `'schedule'` or `'manual'` (the user, also through `until`). Turning it off sends the summary to desktop and Telegram: the schedule's off keeps **Mirador: resumen del turno de noche**; any other off sends **Mirador: resumen del piloto automático**, opening with "Mientras no estabas, Mirador hizo esto:". Agent-facing texts and the decider and judge prompts say the user is away from the keyboard.

### Delegating from a workspace

`POST /api/terminals/batch` takes an optional `instruction` (1-2000 characters after trimming, no control characters but line breaks and tabs) and `autopilot` (boolean, only with an instruction; `reopen` is not allowed with one; else 400 `delegate_invalid`). A new agent gets the instruction as its first message on pi's command line (`agentArgs`: `Task from the user, delegated through Mirador:\n\n<instruction>`, one shell-quoted word; the leading word keeps pi from reading it as an option, an `@file` or a subcommand), only when the agent command is a plain gentle-shell or pi (the same rule as `--session` at a restore), else that folder is `failed`. A folder whose agent is already open gets it as a bridge `message` instead (`NightService.sendNote(id, text, '', taskText)`, logged as kind `note`): `sent` once the bridge confirms, `failed` with the reason otherwise. With `autopilot: true`, once every folder resolved and before anything opens, an autopilot that is off is switched on by hand with no `until`; an on is left as it is. The answer adds `autopilot: 'turned_on' | 'already_on' | 'unavailable'` when it was asked, after `autopilot.json` is written. Each instruction is kept in memory as that terminal's task (`NightService.assignTask`; not in `open-agents.json`, so a restore never sends it again, and gone with the terminal) and reaches the decider as `NightContext.task`, a `<task>` data block after the mission (`night-decider-v3`); it never relaxes the defer rules, and the policy (`checkQuestion`, the follow-up filters) never reads it. `GET /api/night/reminder` lists it per agent (`task`). `POST /api/night/sensitive { text }` → `{ topic }` (policy.ts `findSensitive`, or null; 400 `night_text`) feeds the dialog's warning.

### Schedule, bedtime reminder and execution notes

API: `GET/PUT /api/night/schedule` (`{ enabled, days: 0-6, start: 'HH:MM', end: 'HH:MM', remindBeforeMinutes: 0-240 }` → `{ schedule, timeZone, current, next: { start, end, remindAt }, reminderDue, offUntil }`; 400 `night_schedule`), `GET /api/night/reminder`, `GET/POST /api/night/notes` (`{ workspaceId, terminalId?, text ≤ 2000 }`; 400 `night_note`/`night_note_terminal`, 404 `night_note_workspace`, 409 `night_note_full`), `DELETE /api/night/notes/:id` (404 `night_note_unknown`). Files in `$XDG_STATE_HOME/mirador/night/`: `schedule.json`, `scheduler.json`, `notes.json`, `autopilot.json`, `queue.json` (0600).

**Night queue** (`src/night/night-queue.ts`, owned by `NightService`). While the autopilot is on, at most N agents work at once. What would start an agent (an execution note for an agent that finished or waits, an automatic follow-up when it is due, also from the activation sweep) joins a first-in-first-out queue, one entry per terminal and kind; a note takes the place of that terminal's queued follow-up, and when a note entry starts every note waiting for that terminal goes out, oldest first, each with its own `note` record. The next entry starts on any agent state change (`AttentionStore.onAgentState`), note added, follow-up due, N change, terminal close, or memory poll, while `busy < N` and MemAvailable ≥ the launch gate's reserve (`reserveFor(launchGate.limits)`, config `launches.reserveMb`; an unreadable meminfo never blocks). A granted start holds a claim on its slot until the agent's state turns `working`, its bridge reports the end of a turn, nothing went out, or `CLAIM_MS` (2 min) passed. A note to an agent that is `working` goes out at once, as before; a note to an `unknown` agent waits its turn. A workspace note is marked delivered only once every agent it was for got it in the same activation: an off or shutdown mid-delivery leaves it pending, and the next on in the same process sends it only to the agents it did not reach (that set is kept in memory, so after a restart it goes to all of them again). Turning the autopilot off empties the queue: queued notes stay pending in `notes.json`, queued follow-ups are dropped. Never queued: typing, `sendNote` (a delegated task), `delegate()` and questions. Without `queue` in its options the service starts everything at once (tests that do not exercise the queue).

Windows open on their listed days, in the configured time zone, and may cross midnight. The scheduler turns the autopilot on at the start and off at the end, unless it was on by hand (see Autopilot). Turned off by hand inside a window, it stays off until the next window. The reminder fires once per window, `remindBeforeMinutes` before the start. When the autopilot turns on, pending execution notes are delivered once as `Execution note from the user, who is away from the keyboard:` messages (log kind `note`, never judged); then the agents already finished get the automatic follow-up flow, one every 5 s (kind `auto-follow-up`, `sweep: true`; an unknown final message defers with rule `no-final-message`, which is notified). Registries: `provideNightService`/`nightService` (service.ts) and `provideNightScheduler`/`nightScheduler` with `onReminder` (schedule.ts), keyed by `ctx.terminals`.

### Capacity knobs

The defaults below come from the resource profile (Equilibrado gives the same values); the config keys still win. `engramCacheMs` (default `20000`) is how long one all-projects Engram read is shared by the overview, activity and container summaries; `MIRADOR_ENGRAM_CACHE_MS` overrides it, and tests set `0`. `maxConcurrent` (default `2`) caps the Claude processes running at once across the night decider, the judge and **Mejorar con IA**; extra runs wait in a queue of 32 and are refused as unavailable when it is full. The night decider defers any prompt larger than 48 KiB. The night log answers `recent()` from an in-memory index of about the newest 2 MiB of records, and reads the files only for older windows or after the files change on disk. Cached results (the Engram window, activity, digests, log records) are shared: callers must not mutate them.

### Resource profiles, budget and telemetry

Three profiles change capacity only; no profile has a safety knob, so the policy, the sensitive filters, `MIN_CONFIDENCE` (0.7) and the per-terminal caps are the same in all of them (`test/profiles.test.ts` checks it).

| Knob | `ahorro` | `equilibrado` (default) | `potencia` | Config key that wins |
|---|---|---|---|---|
| `nightBudget`: decider, follow-up and judge calls per night | 60 | 150 | 400 | `nightBudget` |
| `improveBudget`: **Mejorar con IA** runs per day | 100 | 300 | 1000 | none |
| `nightModel`: decider and judge model | `claude-haiku-5-5` | `claude-sonnet-5-5` | `claude-opus-5-5` | `nightModel` |
| `judgeMode` | `doubtful-only`: decisions below 0.85 confidence (or without one) and every follow-up | `every` | `every` | none |
| `maxConcurrent`: Claude processes at once | 1 | 2 | 4 | `maxConcurrent` |

- **Code:** `src/profiles.ts` (`PROFILES`, `effectiveValues`, `ResourceProfiles` with `load`, `values()`, `view()`, `set(name)`, `onChange`), `src/night/budget.ts` (`CallBudget`, `CallTelemetry`, `callMeter`), `src/http/routes/profile.ts`. `server.ts` builds them before the routes and hands them over with `provideProfiles(ctx.terminals, …)` and `provideCallAccounting(ctx.terminals, { budget, telemetry })`; read them with `resourceProfiles(ctx.terminals)` and `callAccounting(ctx.terminals)`.
- **Stored choice:** `$XDG_STATE_HOME/mirador/profile.json` (`{ "profile": "…" }`, 0600). Missing or unknown means `equilibrado`.
- **Runtime switch:** `set()` stores the choice, then its listeners reconfigure the process-wide gate (`configurePiConcurrency`) and the Engram TTL (`EngramClient.setCacheMs`). The decider and judge models, the judge mode and the budget limits are read on every call, so nothing restarts.

| API | Answer |
|---|---|
| `GET /api/profile` | `{ profile, values, overridden, profiles, budget }`. `values` holds the effective knobs, `overridden` lists the config keys that won, `profiles` holds every profile's values, and `budget` is `{ night: { used, limit }, improveToday: { used, limit } }`. |
| `PUT /api/profile` `{ profile }` | The same view after the switch. 400 `profile_invalid` for any other body. |
| `GET /api/telemetry?since=` | `{ since, calls: { [feature]: { [outcome]: n } }, total, totalMs, latency: { [feature]: { p50, p95, runs } }, budget }`. `since` is an ISO time or epoch ms (default: the last 24 h); 400 `telemetry_since`. Latency covers the runs that started a process (not `budget` or `busy`), nearest rank. |

- **Budget:** `$XDG_STATE_HOME/mirador/night/budget.json` (0700/0600). `createPiRunner` charges every run after it holds a gate slot and right before the process starts, in one synchronous step (`CallMeter.take`): parallel runs never both get the last call, and a refusal (`PiRunError` kind `budget`) starts no process. Every run must name its `feature` (`decide`, `follow-up`, `judge`, `propose`) and `promptVersion`; a run without a known feature is refused (`not-started`). The night counter (`decide`, `follow-up`, `judge`) is one per jornada: it starts over when the night schedule's window ends (06:00 without an enabled schedule), also while the autopilot stays on across that time; an off or a restart inside a jornada keeps it, so a day session and that evening's night share one count. While the autopilot is on by hand (`source: 'manual'`) there is no cap: every call is granted and counted, and passing the limit sends one notice per jornada (**Mirador: pasaste el tope de llamadas a Claude**; not persisted, so a restart may repeat it once). While the schedule has it (or it is off) the limit stops calls as below; a handover counts what was already used. **Mejorar con IA** (`propose`) has a counter per day in `timeZone`; a `budget.json` from before S3 keeps it under `translate`, which is read as today's count. When a budget runs out, the decider defers with rule `budget` and the reason `nightly Claude budget reached`, the judge stores `doubtful` with `Nightly Claude budget reached: this move was not reviewed.`, and `POST /api/proposals/improve` answers 429 `proposal_budget`. The first refusal of a night (or a day) sends one notice (`Notifier.budget`, desktop and Telegram) and writes one line to the server log. The morning summary and `GET /api/night/report` add `summary.calls: { used, limit }`.
- **Telemetry:** `$XDG_STATE_HOME/mirador/telemetry/calls.jsonl` (0700/0600), rotated past 5 MiB into `calls.1.jsonl`. One line per run: `{ time, feature, model, promptVersion, ms, outcome, inputBytes, outputBytes }`. `outcome` is `ok`, `timeout`, `error`, `aborted`, `budget` or `busy`, and `ms` counts from the call, waiting for a slot included. Prompts, answers, memory text, terminal text and tokens are never written. An old line with feature `translate` is skipped when read. Prompt versions: `night-decider-v3` (decider.ts), `night-judge-v2` (judge.ts). Bump the version when its prompt changes.
- **UI:** the night panel's **Perfil de recursos / Resource profile** section shows the three options, a table of their values (a row a config key overrides is crossed out and shows the config value), and a meter for the jornada's calls and the **Mejorar con IA** runs used today. The strip shows the jornada's calls as a count only while the autopilot is on by hand (`stripCalls`). `public/features/night-model.js` holds `profileTable`, `profileValue`, `budgetMeter`, `refreshMs` and `reportCalls`. The tracking view reads `GET /api/profile` once at start, and again on the `profile` event the panel emits after a switch, to set its refresh interval.
- **Eval:** `node scripts/eval-night.ts --profile <name>` runs on that profile's model and prints the calls against its nightly budget, without enforcing it (`evals/night/README.md`).

### MCP servers per project

Rules in `src/mcp/project-mcp.ts`, routes in `src/http/routes/mcp.ts`, UI in `public/features/mcp.js` with its pure rules in `public/features/mcp-model.js` (tested in `test/mcp-model.test.ts`), `public/i18n/mcp.js`, `public/styles/mcp.css`. The folder always comes from `ctx.resolveFolder(ws, rel)`; gentle-shell's agent dir is the config key `gentleShellAgentDir`, else `GENTLE_SHELL_HOME`, else `~/.gentle-shell/agent`, and is only read.

| API | Answer |
|---|---|
| `GET /api/mcp?ws=&rel=` | `ProjectMcpView` |
| `PUT /api/mcp` `{ ws, rel, disabled: string[] }` | `ProjectMcpView` plus `saved: { written, excluded }` (`written`: the file changed; `excluded`: a line was appended to the repo's `info/exclude`) |

```ts
ProjectMcpView = {
  file: '.pi/mcp.json', exists: boolean,
  git: 'tracked' | 'ignored' | 'untracked' | 'none' | 'unknown',   // the file in git; none = not a repo, unknown = git failed
  trust: 'trusted' | 'untrusted' | 'unknown',                      // whether pi reads the project file here
  userConfig: 'ok' | 'missing' | 'invalid',                        // <agentDir>/mcp.json
  servers: [{ name, source: 'user' | 'project', enabled: boolean, locked: boolean, description: string | null, estimatedMb: number | null }],
}
```

- `servers`: the user file's servers in its order, then the ones only the project declares (an entry with `command`, `url` or `type`, which replaces a user entry of that name). `enabled` is what agents in the folder start: a project entry's `enabled` wins, else the user entry's. `locked`: the user file turns it off and the project does not turn it on; saving never touches it. `estimatedMb` comes from `MCP_MEMORY_MB` (one measurement, 2026-10-29); others are `null`.
- `disabled` lists the servers off after the save; every other listed server is wanted on. It must be a list of at most 200 listed names, else 400 `mcp_invalid`. An existing file that is not a JSON object with an `mcpServers` object is 409 `mcp_unreadable` (GET and PUT, never overwritten); a `.pi` or `.pi/mcp.json` that is a symlink or not a regular file/folder is 409 `mcp_not_regular`. Unknown workspace 404 `workspace_not_found`, a folder outside its root 400 `folder_invalid`.
- A save turns a server off by setting `enabled: false` on its entry or adding `{ "enabled": false }`, and on by deleting that `enabled` (and a bare override as a whole). Nothing else in the file changes; key order is kept, new overrides go last, the indent (tab or N spaces, 2 for a new file), BOM, final newline and mode are kept; the file is written back with LF line endings and one item per line, so a CRLF or single-line file changes layout while its parsed content stays the same apart from `enabled`. A save with no change writes nothing. Saves of one folder run one at a time.
- Git (read-only `git rev-parse`, `ls-files`, `check-ignore`, with `GIT_*` removed from the environment): when the file was untracked and not ignored, a save appends `/<prefix>.pi/mcp.json` (wildcards escaped) to `git rev-parse --git-path info/exclude`, unless that line is already there.
- Trust (pi docs/security.md, `ProjectTrustStore`): the nearest `true`/`false` in `<agentDir>/trust.json` for the folder's real path or a parent (`null` is no decision), else `defaultProjectTrust` in `<agentDir>/settings.json`: `always` trusted, `never` untrusted, anything else unknown. An extension handling pi's `project_trust` event can still decide otherwise; Mirador cannot see that.

Row actions: `registerRowAction` accepts `folderOnly: true`: folder rows show the button as usual, and workspace rows leave it out (MCP servers are chosen per folder).
