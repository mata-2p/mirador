# Attention and tracking

Where each folder left off, the inbox of agents waiting for you and the tracking view. The summary is in the [README](../README.md#what-it-does).

## Where it left off

- **Workspace summary and where each folder left off.** Selecting a workspace offers a **Resumen / Summary** view: the chosen day across its folders (folders with activity, memories, sessions, the most relevant titles), then one row per folder, most recent work first, with the last day worked there and where it stopped (the latest session summary's goal and next steps, or the latest memory title); long next steps show their first three lines and **Ver más / Show more** opens the rest. One click on a row opens that folder; a folder with no memory offers to start gentle-shell. A selected folder opens on **Dónde quedó / Where it left off**: its last worked date and the latest session summary's next steps and accomplishments. The objective and each folded section (Siguientes pasos, Hecho…) turn pages like a book with ‹ n / m ›, or the arrow keys and PageUp/PageDown while the text has focus, so a long list never makes the sidebar scroll; a short one shows no pager. The panel head switches between **Te esperan (N) / Waiting for you (N)** (the attention inbox), the selection's view (**Resumen** for a workspace, **Dónde quedó** for a folder) and **Día / Day**, which holds the date navigation and the daily summary; the choice is remembered per kind of selection. It costs two Engram reads per workspace (`GET /projects` and one window of all projects), never one per folder. Each workspace can have a mission: Markdown text with its goal, what to watch, how to decide and what never to do. Edit it from the **Misión / Mission** card at the top of the workspace Summary; the night shift reads it when it decides for you. The card shows the first five lines of a long mission, with **Ver más / Show more**. It is stored as `mission` on the workspace in `config.json`, up to 8000 characters, and leaving it empty removes it.
- **Without Engram: Claude Code's last message.** For agents started as Claude Code, Mirador keeps a small local record per folder of what Claude Code's own hooks hand over ([hooks reference](https://code.claude.com/docs/en/hooks)): your last message (`UserPromptSubmit`'s `prompt`, as received, so pasted text arrives already expanded in place and a typed command such as `/deploy staging` as typed), Claude's final message of the turn (`Stop`'s `last_assistant_message`), the latest compaction summary (`PostCompact`'s `compact_summary`) and when and why the session ended (`SessionEnd`'s `reason`; stored, not shown). **Dónde quedó / Where it left off** shows the newer of this record and Engram's latest session summary for the folder, judged by the time of the text it would show (the newer of Claude's final message and the compaction summary; at the same instant, the final message), not by the latest prompt or the session's end: a record that holds only your prompt never wins over an Engram summary, and a tie (same second) goes to Engram. The foot names the source: "From Claude Code's last message · …" (or its compaction summary, or only your last message when the agent has not answered yet), or "Engram session summary · …". That text is read like a session summary: a "Next steps" heading becomes the **Siguientes pasos / Next steps** fold, anything else shows as text; your last message shows above it as plain text, clipped like an excerpt (12 lines). With a record, the view works with Engram stopped or not installed; without one, an unreachable Engram answers as before. Plain mode shows the same record, as plain text, above the git state. The workspace **Resumen / Summary** rows follow the same rule, one record read per folder (the root gets a row for its record too); with a record in any folder, an unreachable Engram still answers from the records, under a notice that Engram is not responding (the folder view shows the same notice when it answers from its record), and without one it answers as before. A block from the record has **Olvidar / Forget**, in both modes: after a confirmation (focus starts on Cancel), it removes that folder's record and the view reloads with Engram's summary or the empty state. No model is called and no agent turn is added.
  - **How it travels.** `bin/claude-hook` sends each field, cut to 16 KiB of UTF-8 on a character boundary with `…` at the end, as one `left-off` line on Mirador's local herdr socket, after the attention report; `SessionEnd` sends its `reason` (lowercase words joined by `_`, at most 64 characters, such as `prompt_input_exit`) instead of a text, with no attention report and within the hook's one-second give-up. It writes nothing itself. The server validates the line (its keys and types, a running agent terminal for its pane, the session id, the size: a longer text is cut the same way, never refused for its length alone) and writes the record; anything else is dropped and writes nothing.
  - **Storage.** One record per workspace and folder: `<stateDir>/left-off/<workspace id>/<hash of the folder>.claude-code.json` (`~/.local/state/mirador/left-off/` by default), folders 0700, files 0600, written atomically. A new Claude Code session replaces the previous one's texts. A `SessionEnd` marks only its own session's record (another session's end, or one with no record, writes nothing), and a later text of the same session clears the end. The format (v1) is `{ v, agent: "claude-code", workspaceId, rel, sessionId, at, lastUserMessage, lastMessage, compactSummary, endedAt?, endReason? }`, each text `{ text, at, truncated? }` or `null`, `endedAt` (the server's time of the `SessionEnd`) and `endReason` both present or both absent (records written before them still read), times in ISO UTC.
  - **Privacy.** The texts are plaintext on disk, like Claude Code's own transcripts, and can quote anything the agent saw or you pasted, secrets included. They are never sent anywhere (not to Engram, the night shift, Telegram or notifications), never logged (only that a write failed, and its error code), and shown only as text. Mirador never reads Claude Code's configuration or transcripts and never writes into `~/.claude` or the repository.
  - **Retention.** Records older than `leftOffDays` (30 by default) are removed when Mirador starts and, at most once an hour, when a record is written; an older record is never shown. A record also goes when you press **Olvidar / Forget** on its block (`DELETE /api/folder/left-off?ws=&rel=`), when you forget that folder's sleeping Claude Code agent (chosen as Claude Code or started as the configured `agentCommand`; forgetting any other agent leaves it), and, with all of its workspace's, when you remove the workspace. `leftOff: false` turns the capture off: the hooks still report attention but forward nothing, and no record is written or read (see [Configuration](configuration.md#configuration)).

## Attention inbox

The panel's **Te esperan (N) / Waiting for you (N)** view lists only the agent terminals waiting for you, in two groups, with how long each has waited: **Needs you** (a guarded command to approve, a questionnaire, a choice, any other dialog, or an agent that stopped with an error) as one list across workspaces, the longest wait on top, each entry naming its workspace and folder; and, below it, **Finished, ready for review** (the agent ended its turn), by workspace and folder. The order is the server's (`GET /api/inbox` and its stream send items already sorted: answers and errors first, then finished turns, the oldest wait first); the view keeps it rather than sorting again. Click an entry (or Tab to it and press Enter) to jump to that terminal; its tab carries a ● (answer) or ✓ (finished) too, and the window title shows the count. The terminal you are looking at is not listed; it comes back if you switch away while it still waits. An answer leaves once the agent is answered; a finished turn once you activate or type into that terminal, or the agent starts again; both leave when the terminal ends. N counts the ones that need your answer; with nothing waiting the view says so.

**Browser notifications** are off until you turn them on with **Activar avisos del navegador / Turn on browser notifications** at the top of the view. That click is the only moment Mirador asks the browser for permission (never on load); the choice is kept in this browser's `localStorage` as `mirador.inboxNotify` (`true` or `false`), and the same button turns them off. While on and allowed, an agent that starts waiting for you or stops with an error shows one notification. It carries Mirador's mark as its icon (a 192 px PNG, with a white badge for Android's status bar; both made from `public/icon.svg` and served by Mirador itself, as PNG because Firefox on Linux shows no image for an SVG icon). The title says who waits and why, `{project} · {reason}`: the project is the folder's last part, or the workspace's name at its root. The body's first line is the question or detail, when there is one; the second names the agent and the full path, `{agent} · {workspace › folder › …}` (only the path when this window does not have that terminal). For an agent in workspace `Dev`, folder `web/mi-proyecto`:

```text
mi-proyecto · Needs you to choose
Which database should the migration use?
Claude Code · Dev › web › mi-proyecto
```

![A Linux desktop notification from Mirador in the invented demo workspace. Title: acme-api · Apply the migration to staging?; below it the site, 127.0.0.1:4746, and the line demo-agent · Demo › acme-api](img/notification.png)

A notification for a blocked agent shows only the project and the reason (`mi-proyecto · {reason}`) with an empty body, unless the agent asks a questionnaire or a choice: never a command, its detail, the agent or the path, because a command can carry a token.

Text from the agent or the disk shows as one line: line breaks and control characters become spaces, invisible format characters (zero-width marks, bidirectional marks, the soft hyphen, tag characters) are dropped, except the zero-width joiner that builds emoji, and it is cut to 120 characters with `…`. Each notification also carries the interface language (`lang`) and the time the wait started (`timestamp`).

A card that asks something of you (a blocker or a dialog) stays on screen until you act on it (`requireInteraction`); an error leaves when the browser hides it, as before. Two switches sit beside the button while notifications can be used, each kept in this browser's `localStorage`: **Los avisos que piden respuesta se quedan hasta que actúes / Notices that need an answer stay until you act** (`mirador.inboxNotifyStay`, on by default; off, every notification leaves when the browser hides it) and **Discretos: sin proyecto ni pregunta, para compartir pantalla / Discreet: no project or question, for screen sharing** (`mirador.inboxNotifyDiscreet`, off by default). Discreet mode is for sharing your screen: a card's title is only **Un agente te espera / An agent is waiting for you**, with an empty body, so no project, question, agent or path shows. On Linux, the desktop's notification history keeps a notification's text after its card closes; discreet mode exists for that too, for screen sharing or a shared machine.

![The same notification in discreet mode: the title An agent is waiting for you, and below it only the site, 127.0.0.1:4746](img/notification-discreet.png)

Notifications wait a moment: the page collects new cards for 1.5 s from the first of them, so a notification may arrive up to 1.5 s after its card shows in the inbox. A card that leaves in that time (answered at once) or that you open never notifies; turning notifications off in that time drops them all. When the 1.5 s end with 1 or 2 new cards, each gets its own notification, showing the card as it is by then (a card that turned from an error into a question shows the question). When 3 or more new cards arrive within those 1.5 s (agents that start waiting at almost the same moment), one notification stands for all of them: **3 agentes te esperan / 3 agents are waiting for you**, with their projects in the body, separated by commas (in discreet mode, the title alone). It stays on screen when any of them asks something and the switch is on, carries the time of the longest wait, and replaces the previous burst's notification, so it also counts that burst's cards that still wait (and stays on screen when one of them asks something). Clicking it brings the window forward and opens the inbox (on a phone its full-screen view; otherwise the panel's **Te esperan / Waiting for you** view, showing the panel first when it is hidden). It closes when the last of its cards leaves.

What did not change: a card is one notification, with its own tag: while a terminal stays in the inbox waiting for you or with an error (also when it goes from blocked to error and back), it does not notify again, and the stream's same snapshot after a reconnect or a re-render does not repeat it. When the card leaves (answered, cleared, the agent died, the terminal closed, or the turn finished), its notification is closed; the agent's next wait notifies again. Notifications shown before a reload are not known to the new page and stay until you dismiss them. What already waits when the page opens, what started while notifications were off, and the terminal you are looking at do not notify. Clicking a card's notification brings the window forward and selects that terminal when this window has it; a notification whose card or terminal is gone only brings the window forward. Finished turns never notify. If the browser has no Notification API, or blocked notifications for the site, the view says so (**not available** or **blocked by the browser**) and everything else works as before. There is no service worker, no sound and no network call or Content-Security-Policy change: the notification is the browser's own, and its icon comes from Mirador's own server.

**On a phone.** This view is experimental in 0.2.0: what was measured on a real phone, how to get out of **Reconectando… / Reconnecting…** and the limits of finger scrolling are in [The phone inbox is experimental](#the-phone-inbox-is-experimental). Through the SSH tunnel of [docs/security.md](security.md#on-a-phone), a phone opens Mirador in its own browser. In a window 600 px wide or narrower (the width alone decides; a touch screen does not) the page opens on this inbox as a full-screen view instead of the terminal deck. A sticky header shows **Te esperan (N) / Waiting for you (N)**, N counted as in the panel, and the state of the inbox stream: **En vivo / Live** while `GET /api/inbox/stream` reads, **Reconectando… / Reconnecting…** before its first answer, between retries, and as soon as the stream goes silent. The server writes a heartbeat every 25 s, so a stream that reads nothing, not even a heartbeat, for 60 s (two heartbeats plus 10 s) is dropped and reopened with the usual backoff (1 s, doubling up to 30 s); the header shows **Live** again once the new one answers. A phone browser suspends a tab in the background, and the SSH tunnel can die meanwhile while the local socket stays open: when the tab comes back after 60 s or more hidden, or to a stream that has read nothing for 60 s, the inbox does not trust the old connection and reconnects at once, without the backoff. A short switch away and back keeps the stream as it is, and a hidden tab never retries faster than the backoff. Every window follows the stream this way; only the phone header shows its state. The header's **Terminales / Terminals** goes back to the deck, whose top bar then has a **Te esperan (N)** button back to the inbox; **Abrir la interfaz completa / Open the full interface**, under the cards, opens the same full UI (the sidebar and the panel as drawers, files, the autopilot and settings). Each card takes the full width, in a larger text: the reason first, then workspace › folder (finished cards name their workspace too), then how long it has waited, then its detail; **Abrir / Open** for a named file sits under it. While the inbox covers the deck, the terminal that was active is listed too. Tapping a card opens that terminal full-screen in the same xterm, without raising the soft keyboard (tap the terminal to type), over a key bar: **Esc**, **Tab**, the four arrows and **Enter**, each sending the bytes a keyboard sends to that terminal (the arrows as `ESC [ A`–`D`, or `ESC O A`–`D` while the program asked for application cursor keys). There are no digit keys yet: they come once each agent's menus are verified to accept them. The terminal's back control, or the terminal closing, returns to the inbox. The terminal takes the phone's size, and the pty keeps the last size any window sent, as with any second window: a desktop window showing it takes its size back when it is focused again. Above 600 px nothing changes.

**Touch targets.** On a coarse (touch) pointer, at any width, the cards, **open file**, the notification button and every segment button are at least 44×44 CSS px (WCAG 2.5.5, Target Size, Enhanced) and spaced so none overlaps; the layout itself does not change.

How it learns: Mirador stands in for [herdr](https://github.com/Gentleman-Programming/gentle-shell/blob/main/docs/readme-reference.md#herdr-active-work-summary) in agent terminals only. They get `HERDR_ENV=1`, `HERDR_PANE_ID` (the terminal id), `HERDR_SOCKET_PATH` and `HERDR_BIN_PATH`; gentle-shell then reports through `herdr pane report-metadata`, which in Mirador is `bin/herdr-shim`, forwarding one JSON line to a Unix socket in `<runtime>/mirador/herdr/` (folder 0700, socket 0600; no network listener). Reports are size-limited, validated, shown as text only, and ignored for unknown, shell or finished terminals. If the shim or the socket fails, gentle-shell carries on as usual.

gentle-shell itself only reports its current Todo title. The "waiting for you" signal (`herdr:blocked`) stays inside the agent unless a bridge extension carries it, so Mirador starts agents with its own bridge: when `agentCommand` is a plain `gentle-shell` or `pi` command (no `;`, `|`, redirections or substitutions), agent terminals run it with `-e <mirador>/src/attention/gentle-shell-bridge.ts` appended. Nothing is written to agent homes or to your config; set `"attentionBridge": false` in `config.json` to start agents exactly as configured.

Other agents have attention and resume only where Mirador can bring its bridge per launch, again without writing to their config: **Claude Code** gets its hooks from a settings file passed with `--settings` and resumes with `--resume <id>`; **opencode** (2.x) gets a plugin named in `OPENCODE_CONFIG_CONTENT` and loaded by a private server (`--standalone`), and resumes with `--session <id>`; **Antigravity** (`agy`) gets its hooks from a folder of Mirador's added as a workspace folder with `--add-dir`, and resumes with `--conversation <id>` (known limits: the id can go stale after `/resume`, and the agent sees that folder as a second workspace folder). Codex, Gemini CLI and Kimi start without attention and always in a fresh session. Kimi Code CLI reads its hooks only from your own `~/.kimi-code/config.toml` and its installed plugins, with no way to add them for one launch, so Mirador leaves kimi as you configured it: no inbox entries, and a restore or wake starts a new kimi session (inside it, `/sessions` picks an older one). The details are in [docs/extending.md](extending.md).

The bridge reports three cases, kept apart: a gentle-ai blocker (`herdr:blocked`: guarded command, questionnaire, choice), any extension dialog the agent waits on (pi's `ui_prompt_start`/`ui_prompt_end` with its title: review consent, review-authority confirms, prompts forwarded from subagents, …), and a finished turn (`agent_settled`), which ranks lower and stays until you type into or activate that terminal, or the agent starts again. Prompts pi draws without an extension dialog are not seen. Inside these terminals gentle-shell also keeps pi's native "Working…" row, as it does under herdr.

**OSC 7501 (Program Status Protocol).** Any program in an agent terminal can also say what it is doing itself, in its own output, with the [Program Status Protocol](https://www.superlogical.com/rex/docs/build/program-status) (revision 0.4): `ESC ] 7501 ; state=…:kind=…:msg=<base64> ST`, ended by `ESC \` or BEL. Mirador reads it from each pty before the scrollback and the browser see the output, so the raw sequences never reach the screen, and it answers the probe `ESC ] 7501 ; ?` with `ESC ] 7501 ; ?` (programs such as pi and Claude Code only report once the terminal answers). While a terminal holds a report it wins over the hooks above: `blocked` (with `kind` permission, question or auth, and its message as the label) is an answer card, `done` a finished card, `error` an **error** card ("Stopped with an error", its message below) that leaves once you type into that terminal (activating the terminal only hides the card while it is in view; it comes back when you switch away), and `working` or `idle` show no card; `state=clear` drops the reports and the hooks decide again, and a new shell prompt marked with OSC 133 A (shell integration) drops `working` and `blocked`. One exception: a wait the hooks report (a gentle-ai blocker or a dialog: their `blocked` or `prompt`) wins over a `working`, `done` or `idle` report, so an agent whose program keeps saying `working` while a dialog waits (gentle's questionnaire) still shows **Needs you**, notifies once, counts as waiting in the bedtime reminder and is never put to sleep for idling. A `blocked` report keeps deciding: when the hooks report the same wait later (Claude Code reports a permission by both, OSC first), there is still one card, the program's, and one notification. An `error` report also keeps deciding over a hook wait (unchanged: it is a card that needs you already). The hook wait ends when the program then reports `done`, `idle` or `state=clear` for its root record (no `id`), or when its `blocked` report ends (the program saw the answer, for example `blocked` then `working`), so no card is left behind after the answer. A `done` or `idle` from a child record (one with an `id`), or a `state=clear` scoped to an `id`, leaves the hook wait open; that clear still drops the records it names. Per turn, once the program's `blocked` report of kind `permission` has ended (it was answered), a later hook `prompt` (Claude Code's permission notice, which comes some seconds after the program's report) is ignored when it arrives alone: no card and no notification (a `prompt` reported together with a hook `blocked` keeps its text on that card). The rule holds until the next turn starts, which is the program's first `working` after a `done`, an `idle` or the hooks' finished turn (Claude Code's Stop); those closing reports alone do not end it, so a late notice after a short turn is ignored too. The agent leaving (its terminal's bash prompt) or a `state=clear` resets it at once. A hook `blocked` (a gentle-ai blocker) is never ignored. Known limits: if the turn ends and you send another prompt right away, the program's `working` starts the next turn, and the previous turn's late notice, arriving after that, raises a card; and a second dialog in the same turn that only the hooks report as a `prompt` (the program does not report it) gets no card until the next turn. Otherwise any live report, even `idle`, still hides the other cards the hooks report (a finished turn) until `state=clear`, or until a prompt drops the last `working` or `blocked` record; `idle`, `done` and `error` survive a prompt, so only `clear` (or the terminal ending) hands back from them. `GET /api/terminals` gives each agent terminal its `agentState` (`working`, `waiting`, `finished`, `error` or `unknown`). Reports are validated as the protocol says (unknown keys ignored; bad base64, a control character or a size over the limits discards the report) and shown as plain text only. Nothing is sent back except the probe answer. Mirador differs from the protocol in three places: it does not read the 8-bit C1 forms of OSC and ST (a C1 ST inside a sequence cancels it, as CAN, SUB or any ESC other than `ESC \` do, and the bytes pass through unchanged), a full reset (RIS) does not drop the records, and a report whose `id` is malformed is ignored whole instead of losing only that pair. Agent terminals mark every prompt their bash draws (OSC 133 A), so an agent that exits or dies loses its `working` and `blocked` reports at once. That prompt also ends the wait its hooks reported (their `blocked` and `prompt`, as when a hooks-only Claude Code dies at a permission question), so its card leaves and does not notify again; a finished turn stays, and the agent reads `unknown` until its next report. It also ends the hooks' last `working` report with no finished turn (a turn cut without Stop, by an interrupt or a crash, and then the agent exits), so that agent reads `unknown` until its next report too, instead of staying `working`. It only ever ends the wait or the `working` of that same terminal: every hook report names the terminal it came from (`HERDR_PANE_ID`, set per pty), and Mirador never attributes a report to a folder, so a prompt in one terminal never ends the wait or the `working` of another terminal open in the same folder. If a folder-wide attribution is ever added, such a wait must stay while more than one terminal is open in that folder (a stale card over a lost notice). An agent in `error` waits for you like a blocked one: **Seguimiento / Tracking** lists it under **Needs you** with "Stopped with an error", the sidebar, its tab and its pane show the error state, idle sleep never counts it as idle, and its open-agents record keeps `error`, so it reopens after a restart instead of sleeping.

### The phone inbox is experimental

In 0.2.0 the phone inbox is experimental. It was tested on one phone: an iPhone 11 with iOS 27.0.1 and Safari, reaching Mirador through an iOS SSH app (Termius) with a local forward of port 4545, as in [docs/security.md](security.md#on-a-phone). It has not been tried on Android yet (#71).

**What was measured.** On that phone:

- Switching to another app for a short while, or locking and unlocking the phone, keeps the header on **En vivo / Live**.
- Closing the host terminal where you ran `mirador link` does not end the phone's session.
- After about 4 minutes outside Safari, the header showed **Reconectando… / Reconnecting…**: iOS had stopped the SSH app's forward in the background. Turning the forward back on in the SSH app brought **Live** back, without a new link.
- Once, after about 30 minutes away, the page asked for a new link. The cause is not confirmed (#95).

iOS does not keep an SSH app's forward running in the background for long. A way to reach the inbox that does not depend on it is a design issue (#72).

**Getting out of Reconnecting….** The header shows **Reconnecting…** whenever the inbox stream is down, whatever the cause. Try these in order:

1. Open the SSH app and check that the forward of port 4545 is running; if it stopped, start it again. Back in the browser, the header returns to **Live** by itself within 30 s (the longest wait between retries); reloading the page reconnects at once.
2. If the page shows **La sesión expiró / Session expired**, the session is over: Mirador restarted, another window pressed **Cerrar sesión en las demás ventanas / Sign out the other windows**, or 32 newer sessions pushed it out. No retry brings it back: run `mirador link` on the host and open the new link within 60 s. After a sign-out from another window, the header behind that notice still says **Reconnecting…** (#93).
3. If the forward is running and a reload neither brings **Live** back nor shows **Session expired**, check on the host that Mirador is running: `mirador link` says `mirador: not running` when it is not.

**Scrolling with a finger.** A finger dragged over a terminal scrolls that terminal, in the view a card opens and in the full interface alike:

- In programs that do not track the mouse, such as Claude Code or a shell, the drag scrolls the history and the text follows the finger; typing or a key-bar key goes back to the end.
- Programs that track the mouse, such as gentle-shell or `fzf --height`, get the drag as the mouse wheel.
- Full-screen programs that do not track the mouse, such as `vim` or `less`, get nothing from the drag (#87).
- In the full interface (**Abrir la interfaz completa / Open the full interface**) the drag scrolls the terminal under the finger, and the page still pans everywhere outside a terminal; that terminal has no key bar yet (#81).
- The drag has no momentum. The terminal uses a 12 px font, and pinch-zoom does not work over it (#89).

**Known issues.**

- **Olvidar / Forget** on a sleeping agent in another window does not reach the phone: it keeps showing the agent asleep until a reload (#91).
- The title counts only the cards that wait for an answer, so it can read **Te esperan (0) / Waiting for you (0)** with a **Terminó su turno / Finished its turn** card on screen (#92).
- In the full interface, the agent chooser of a workspace-tree row and the side panel's tab strip overflow the screen (#82, #83).

## Tracking view

**Seguimiento / Tracking** in the top bar hides the development layout (its terminals keep running) and shows what is happening across workspaces; **Desarrollo / Development** brings the layout back, and Mirador remembers the choice per window. It reads `GET /api/terminals`, `GET /api/inbox` and `GET /api/activity` for today when shown and every 15 s while it stays visible, and stops reading when you leave it or the window is hidden.

The view fills the window without a page scroll: every lane and dock pane is a labelled region with its own scroll (Tab reaches it, the arrow keys scroll it), so a long list never pushes the rest down. On a window narrower than 900 px the modules stack and the view scrolls, each module keeping a bounded height.

- **Strip:** projects advancing today (folders with a running agent terminal plus Engram projects with memory saved today, counted once when a folder and a project share a name), agents running, and the **Piloto automático / Autopilot** (its switch is **Turno de noche** under **Ajustes**: on by hand it asks "hasta las HH:MM" or "hasta que lo apague"; the night shift schedule turns it on and off by itself): its state (who switched it on, since and until when), the Claude calls of the jornada (a count only while on by hand, which has no cap), and two buttons, **Antes de dormir / Before bed** and **Ajustes del turno / Shift settings** (schedule, agents working at once, resource profile with the budget, Telegram bot), each in a dialog. In **Ajustes del turno** each part is folded with its value on one line («Lun–Vie 23:00–07:00» or «Apagado», «5 a la vez», «Equilibrado», «Conectado» / «Sin configurar»); its explanation sits behind a small **Cómo funciona / How it works**. An error or a save message shows under the folded part, and a new error opens it. The profile table folds under «Qué fija cada perfil» and opens by itself when config.json overrides a row. While the autopilot is on it also says how many agents work of N and how many wait in the night queue. What you type there survives the polling and closing the dialog.
  - **Who turns the autopilot off.** An on by hand outlives window starts and ends, and survives a restart. A start without the night socket keeps it: it comes back at the next start, and an open window cannot take it over. A manual "hasta las HH:MM" that passes inside an open window hands it to the schedule, and the window end turns it off. An until exactly at a window end is outside the window, because the end is not part of it: the autopilot turns off then as your off and the next window starts as usual.
  - **Activation log.** Every on, off, take-over by hand, handover to the schedule, until change and shutdown is a line in `~/.local/state/mirador/night/activations.jsonl` (0600, the latest 500 kept). Each line holds the state before and after and the cause: `user` (older lines that hold the legacy value, `LEGACY_USER_VALUES.cause` in `src/night/legacy-owner.ts`, are listed as `user`), `delegation` (a delegation's "Prender el piloto automático"), `until`, `handover`, `window-start`, `window-end`, `shutdown`, or `restart-resume` / `restart-deferred` / `restart-dropped` for a saved manual on at a start. `GET /api/night/activations?limit=` lists them latest first (default 100).
- **Lanes, by what each agent needs from you:** **Te necesita / Needs you** (agents waiting for your answer or stopped with an error, in one list, what the night shift left for you, notes Mirador left for a terminal), **Para revisar / To review** (agents that finished their turn, then what Mirador resolved that you have not seen), **Trabajando / Working** (only the agents running now, and the count of bash terminals), and **Lo que hizo Mirador / What Mirador did** (the night report: each row shows its summary, the judge's verdict and the time; **Detalles / Details** opens what it did, why, its confidence and the judge's note; your Right / Wrong stays on the row). Each terminal shows only in its most urgent lane (needs you, then to review, then working). An agent whose error or finished card you already saw keeps its lane, because the view also reads the state `GET /api/terminals` reports; with no card it shows no label and counts from the terminal's start. The sidebar, tabs and panes read only the inbox, so there it shows as working. Each lane is oldest first, so the one that has waited longest leads; the count in its head is what needs action. A card shows its workspace and last folder as a chip (the whole path is its tooltip), how long, the blocker and what it works on; click one to return to Development on that terminal.
- **Dock, collapsible:** **Historial y métricas de hoy / Today's history and metrics** with the three charts (memories per hour, agent states, memories per project), the Engram projects with activity today (memory count, last time, latest titles), **Cerrados y fuera de Mirador / Closed and outside Mirador** (closed agents, oldest first, and the Engram projects active today with no running agent in Mirador), and the memory health, read only when you press **Revisar ahora / Check now**. Mirador remembers whether the dock is open.

Agents started outside Mirador are not listed as agents: they show up only through the memories they save in Engram, under **Fuera de Mirador / Outside Mirador**.

While the Tracking view is shown, the sheet's Tabs/Grid row and the top bar's free-memory figure (the strip shows it) are hidden, because they only apply to Development; the EN/ES row stays and translates everything in the view, charts included. The charts are inline SVG with a text equivalent for screen readers.
